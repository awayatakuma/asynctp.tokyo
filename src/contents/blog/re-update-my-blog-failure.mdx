2026年5月、私は自分のブログを「Next.js 15」と「React 19」へアップデートしようと試みた。
結果から言えば、**その試みは無惨な崩壊とともに失敗し、私は Next.js 14 / React 18 への切り戻し（リバート）を余儀なくされた。**

クラウドエンジニアとしてインフラの堅牢性を重視する私が、なぜ自分の足元にこれほど脆い「魑魅魍魎」を飼い慣らしてしまったのか。その原因と、現代フロントエンドの過酷な潮流を記録しておく。

## 1. 負債の原点：2年前の「無理やりな結婚」

このブログの負債は、2年前に書いた記事 [「The way how to deal with mdx files in Next.js in app router age」](/blog/how-to-deal-with-mdx) の時点ですでに始まっていた。

当時、Next.js の App Router 環境で MDX を「動的に（外部ファイルとして）」管理する正攻法は確立されていなかった。公式ドキュメントは短く、静的な配置しか想定していなかった。そこで私は `next-mdx-remote/rsc` を使い、`mdx-components.tsx` を無理やり差し込むという、いわば「非公式なハック」に近い形でシステムを組み上げた。

当時の記事でもこう書いている：
> 「Unfortunately, mdx-components.tsx and Remote MDX are incompatible. But you can use mdx-components.tsx in perse processes of mdx.」

この **「本来互換性のないものを無理やり繋ぎ合わせた実装」** こそが、全ての崩壊の起点だった。

## 2. 負債の上に負債を重ねる：Chakra UI という甘い罠

MDX の不安定な基盤の上に、さらに **Chakra UI v2** という重厚なレイヤーを重ねた。
Chakra UI は Emotion に依存し、実行時に JavaScript でスタイルを生成する「Runtime CSS-in-JS」の代表格だ。

- 開発効率は爆速だった。
- しかし、Next.js が「Server Components (RSC)」へと舵を切る中で、この「ブラウザの JS に依存するスタイル」は次第にアーキテクチャの異物となっていった。

基盤が脆弱なまま、その上に便利なライブラリを積み上げる。インフラエンジニアであれば絶対に避ける「負債のミルフィーユ」を、私はフロントエンドで再現してしまっていた。

## 3. 崩壊：Next.js 15 と React 19 の衝撃

そして 2026 年、アップデートという名の「土台の入れ替え」が行われたとき、建物は一気に崩壊した。

### Next.js 15 の破壊的変更
動的ルーティングの `params` や `searchParams` が Promise に変更された。
これにより、既存の全てのページコンポーネントで `await` が必須となり、型定義から実装まで芋蔓式に修正を迫られた。

### React 19 の「自爆」
最悪だったのは、React 19 の開発モードに導入された **「Owner Stacks」** というデバッグ機能だ。
これは要素の生成元を追跡し、より詳細なスタックトレースを出すための「親切な機能」のはずだった。しかし、`next-mdx-remote` が生成する複雑な VDOM ツリーを前にして、この機能自体がパニックを起こした。

```bash
 ⨯ [TypeError: Cannot read properties of undefined (reading 'recentlyCreatedOwnerStacks')]
```

画面には何も表示されず、コンソールを埋め尽くすこのエラー。
**「React がバグを報告しようとして、その報告機能自体がバグって落ちる」** という、まさに魑魅魍魎の極致である。

## 4. 背景となる公式の「断絶」声明

この崩壊は、ライブラリ作者の怠慢ではない。React/Next.js チームによる「意図的な断絶」が背景にある。

React 19 のリリースに関連し、コアチーム（Dan Abramov 氏ら）や Next.js メンテナは、一貫して以下のようなニュアンスの発信を続けている。

> 「Runtime CSS-in-JS (Emotion / Styled-components) は、RSC の並行レンダリングやストリーミングと根本的に相性が悪い。将来的に、パフォーマンスと安定性を求めるなら、Tailwind CSS やゼロランタイムな CSS ツールへの移行を強く推奨する。」

これに応じる形で、Chakra UI も v3 で設計を完全に刷新した。しかし、v2 から v3 への道はもはや「アップデート」ではなく「フルリビルド」に近い。
つまり、**私のような「にわか」が便利だと思って使っていたライブラリは、プラットフォームの進化によって「切り捨てられた」のである。**

## 5. 結論： survival by revert

私は、アップデートを完遂することを諦めた。
`recentlyCreatedOwnerStacks` のエラーを回避するために `use client` を多用し、サーバーサイドの利点を殺してまで最新版に居座ることに、クラウドエンジニアとしての合理性を見出せなかったからだ。

最終的に、私は **Next.js 14.2 / React 18.3** へのダウングレードを選択した。
これは敗北ではない。**「動かない最新」よりも「動くレガシー」の方が、価値を生む（記事が書ける）** からだ。

## 次の戦いへの教訓

今回の「魑魅魍魎」との戦いで学んだことは重い。

1. **魔法の賞味期限**: 「爆速で UI が作れる」魔法のライブラリは、フレームワークのメジャーアップデート時に高確率で「負債の時限爆弾」になる。
2. **疎結合への回帰**: 次の移行先は **Astro** と **Tailwind CSS** に決めている。
    - MDX（コンテンツ）を Next.js という「重すぎる器」から物理的に分離する。
    - CSS を「ただのクラス名」に戻し、React の内部挙動に左右されない堅牢さを取り戻す。

フロントエンド専業ではない人間にとって、Next.js のApp Routerはもはや「メンテナンス可能な範囲」を超えつつある。
次は、もっと「予測可能」で「インフラに優しい」 Astro の海へ、この MDX 資産だけを持って漕ぎ出すつもりだ。

それまでは、この延命されたヴィンテージな Next.js 14 環境で、負債を噛み締めながら文字を刻み続けることにする。
